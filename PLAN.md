# Kaif Board — корпоративная доска задач

> Полный технический план проекта. Документ живой: по мере реализации разделы помечаются статусом.
> Версия плана: 1.0 · Дата: 2026-08-25

---

## 1. Что строим

Корпоративный таск-трекер уровня Jira/Linear для команды, с авторизацией только через Telegram
и глубокой интеграцией с Telegram-ботом (уведомления + быстрые действия). Self-hosted на своём VPS.

**Ключевые принципы:**

1. **Безопасность по умолчанию** — авторизация через Telegram проверяется криптографически, токены короткоживущие, все действия логируются.
2. **Нет «пустых» действий** — каждое изменение статуса назад / переноса дедлайна требует объяснения. Это ядро процесса, а не украшение.
3. **Мобильный клиент — первого класса**, а не «ужатая десктопная вёрстка».
4. **Реалтайм** — доска у всех участников обновляется мгновенно, без F5.
5. **Прозрачность** — полная история задачи, кто что и когда сделал.

## 4. Модель данных

### 4.1 Пользователи и сессии

**User**
- `id`, `telegramId` (BigInt, unique), `tgUsername`, `displayName`, `avatarUrl`, `avatarSource` (telegram/upload)
- `globalRole`: `SUPERADMIN | USER` — суперадмин видит всё, включая все доски (требование «админ видит все задачи»)
- `profileCompleted` (bool) — **обязательный онбординг: имя + аватар после привязки TG**
- `timezone` (по умолчанию из TG/браузера), `locale` (ru/en)
- `botChatId` — chat_id для уведомлений; `botBlocked` — если юзер заблокировал бота
- `notificationPrefs` (JSONB) — тонкая настройка каналов и типов событий, «тихие часы»
- `isActive`, `lastSeenAt`, `createdAt`, `updatedAt`

**Session** — одна строка = одно устройство
- `refreshTokenHash` (SHA-256, не сам токен), `family` (для reuse-detection), `userAgent`, `ip`, `expiresAt`, `revokedAt`, `replacedById`, `lastUsedAt`
- Пользователь видит список своих сессий и может «выйти на всех устройствах».

**LoginToken** — одноразовый код для входа через бота
- `tokenHash`, `status` (PENDING/APPROVED/CONSUMED/EXPIRED), `userId?`, `ip`, `userAgent`, `expiresAt` (2 мин), `consumedAt`

**SecurityEvent** — аудит безопасности (вход, выход, смена роли, отзыв сессии, неудачная верификация подписи).

### 4.2 Доски

**Board**
- `id`, `key` (короткий, `OPS`, `DEV` — из него растут ключи задач `OPS-128`), `name`, `description`, `color`, `icon`
- `ownerId` — **создатель = владелец автоматически**, `isArchived`, `taskCounter`
- `settings` (JSONB): WIP-лимиты по колонкам, обязательность тестировщика, правила «требовать комментарий», рабочие часы/дни для расчёта SLA, дефолтный исполнитель

**BoardMember** — `boardId + userId` unique, `role`: `OWNER | ADMIN | MEMBER | VIEWER`, `addedById`

**Column** — 6 фиксированных колонок создаются при создании доски:
`TODO → ON_HOLD → IN_PROGRESS → QA → READY_TO_RELEASE → DONE`
Хранятся строками, а не хардкодом в UI: у колонки есть `wipLimit`, `order`, `name` (переименовать можно, семантика `key` — нет).

**Label** — `boardId`, `name`, `color`, `description`. unique(boardId, name).

**Sprint** *(опционально, этап 2)* — `name`, `goal`, `startsAt`, `endsAt`, `state`.

### 4.3 Задачи

**Task**
- Идентификация: `id`, `boardId`, `number` (инкремент внутри доски), `key` (`OPS-128`) — по нему ищут и упоминают
- Контент: `title`, `descriptionJson` (TipTap JSON), `descriptionText` (plain-text для поиска), `type` (`TASK | BUG | STORY | EPIC | CHORE`), `priority` (`LOWEST | LOW | MEDIUM | HIGH | URGENT | BLOCKER`)
- Положение: `columnKey`, `rank` (строковый fractional index — надёжнее float, не требует переиндексации всей колонки), `isBacklog`
- Люди: `reporterId` (автор), `assigneeId`, `testerId`
- Оценки: `storyPoints`, `estimateMinutes`, `spentMinutes`
- Сроки: `startDate`, `dueDate`, `dueDateChangedCount`, `completedAt`
- Служебное: `archivedAt`, `createdAt`, `updatedAt`, `lastActivityAt`
- Индексы: (boardId, columnKey, rank), (assigneeId, dueDate), GIN по `searchVector`

**TaskLabel** (m2m), **TaskLink** (`BLOCKS / BLOCKED_BY / RELATES / DUPLICATES` + защита от циклов),
**Checklist / ChecklistItem** (подзадачи с прогресс-баром),
**TaskParticipant** — `taskId + userId`, `role`: `REPORTER | ASSIGNEE | TESTER | WATCHER | CONTRIBUTOR`
> **Ключевая механика:** любой, кто оставил комментарий / приложил файл / изменил задачу и не был участником — автоматически становится `CONTRIBUTOR` и с этого момента получает уведомления по задаче. Отписаться можно вручную (кнопка «Не следить»).

**Comment**
- `taskId`, `authorId`, `bodyJson`, `bodyText`, `parentId` (треды), `editedAt`, `deletedAt` (soft delete — история не рвётся)
- `kind`: `USER | SYSTEM` — системные комментарии создаёт сам сервер при смене статуса/дедлайна с причиной; они визуально отличаются и не редактируются
- `systemMeta` (JSONB): что именно изменилось (from/to), чтобы красиво отрисовать

**Attachment** — `taskId?`, `commentId?`, `uploaderId`, `filename`, `storedName`, `mime`, `size`, `checksum` (sha256, дедупликация), `width/height`, `thumbKey`

**Activity** — полная лента: `boardId`, `taskId?`, `actorId`, `type`, `payload` (diff). Отсюда рисуется таймлайн задачи и лента доски.

**Notification** — `userId`, `type`, `boardId?`, `taskId?`, `actorId?`, `payload`, `readAt`, `telegramSentAt`, `telegramMessageId`.

## 5. Роли и права

### Глобальные роли
- **SUPERADMIN** — видит все доски и все задачи, имеет доступ к админ-панели, банку бэклога по всем доскам, управлению пользователями. (Требование: «админ видит все задачи».)
- **USER** — обычный сотрудник.

### Роли на доске
| Действие | OWNER | ADMIN | MEMBER | VIEWER |
|---|:--:|:--:|:--:|:--:|
| Смотреть доску и задачи | ✓ | ✓ | ✓ | ✓ |
| Создавать задачи | ✓ | ✓ | ✓ | — |
| Редактировать любую задачу | ✓ | ✓ | ✓* | — |
| Двигать задачи между колонками | ✓ | ✓ | ✓ | — |
| Комментировать | ✓ | ✓ | ✓ | ✓** |
| Удалять/архивировать задачи | ✓ | ✓ | автор своей | — |
| Управлять лейблами и колонками | ✓ | ✓ | — | — |
| Приглашать/исключать участников | ✓ | ✓ | — | — |
| Менять роли участников | ✓ | ниже своей | — | — |
| Настройки доски, WIP-лимиты | ✓ | ✓ | — | — |
| Передать владение / удалить доску | ✓ | — | — | — |

`*` — как в Jira: MEMBER правит задачи свободно, но опасные операции (удаление, смена автора) — нет.
`**` — комментарии VIEWER можно отключить в настройках доски.

**Создатель доски автоматически становится OWNER** — запись `BoardMember(role=OWNER)` создаётся в одной транзакции с доской. Владелец у доски всегда ровно один; передача владения — явное действие с подтверждением.

Права проверяются **на сервере** в едином модуле `lib/rbac.ts` (матрица `can(user, action, resource)`), клиент лишь прячет кнопки. Никаких проверок «только на фронте».

## 6. Авторизация через Telegram

Поддерживаем три входа, все три верифицируются криптографически:

### 6.1 Вход через бота по одноразовому коду (основной, самый безопасный)
1. Фронт запрашивает `POST /auth/telegram/login-code` → сервер генерирует случайный 32-байтный код, кладёт **хеш** в БД со сроком 2 минуты, возвращает клиенту код и ссылку `https://t.me/<bot>?start=<code>`.
2. Пользователь жмёт кнопку → открывается бот → `/start <code>`.
3. Бот **достоверно знает** `telegram_id` отправителя (сообщение пришло от Telegram-серверов) → помечает код `APPROVED` и привязывает пользователя.
4. Фронт всё это время слушает статус (SSE/поллинг раз в 2 с) → как только `APPROVED`, делает `POST /auth/telegram/exchange` с кодом → получает пару токенов, код становится `CONSUMED`.

Почему это лучше: не зависит от домена, не требует Login Widget, код одноразовый, срок жизни 2 минуты, и сразу же появляется `botChatId` — то есть уведомления работают с первой секунды.

### 6.2 Telegram Login Widget
Проверка по документации: строим `data_check_string` из отсортированных полей, ключ `secret = SHA256(bot_token)`, сверяем `HMAC-SHA256` в **constant-time**. Дополнительно:
- `auth_date` не старше 5 минут;
- хеш кладём в Redis на 10 минут → **защита от replay**;
- проверка `Origin`/`Referer`.

### 6.3 Telegram Mini App (`initData`)
Ключ считается иначе: `secret = HMAC-SHA256(bot_token, "WebAppData")`. Отдельная ветка кода, те же проверки свежести и replay. Даёт бесшовный вход прямо внутри Telegram — доска открывается как Mini App.

### 6.4 Токены и сессии
- **Access JWT** — 15 минут, хранится **в памяти вкладки** (не в localStorage → XSS не уносит долгоживущий токен). В payload: `sub`, `sid`, `role`, `ver`.
- **Refresh token** — 30 дней, случайные 64 байта, в БД только SHA-256-хеш, отдаётся браузеру в cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/auth`.
- **Ротация при каждом обновлении** + **reuse detection**: если пришёл уже использованный refresh — вся «семья» сессий отзывается, пользователю прилетает уведомление в Telegram «кто-то пытался войти».
- Мгновенный отзыв: поле `tokenVersion` у пользователя + проверка `sid` в Redis-денилисте.
- Socket.IO авторизуется тем же access-токеном на handshake и переподключается при ротации.

### 6.5 Обязательный онбординг
После первой привязки Telegram пользователь получает `profileCompleted = false` и **не может ничего делать**, кроме экрана онбординга: ввести отображаемое имя (2–48 символов) и подтвердить/загрузить аватар (подтягиваем из Telegram, если он открыт, либо загружаем свой). Middleware `requireCompleteProfile` блокирует остальные ручки.

## 7. Безопасность (чек-лист)

**Транспорт и заголовки**
- HTTPS обязателен (Caddy + автоматический Let's Encrypt), HSTS.
- Helmet: строгий **CSP** (без `unsafe-inline`, nonce для скриптов), `X-Frame-Options` (кроме домена Telegram для Mini App), `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff`, `Permissions-Policy`.
- CORS — белый список ровно одного origin, `credentials: true`.

**Аутентификация/сессии** — см. §6. Плюс: проверка `Origin` на всех мутирующих запросах (CSRF-защита в дополнение к `SameSite=Strict`).

**Ввод**
- Всё валидируется zod-схемами (типы, длины, форматы, whitelisting полей). Неизвестные поля отбрасываются.
- Rich-text: на сервере санитайзится (`sanitize-html`) — вырезаются `script`, `iframe`, `on*`-атрибуты, `javascript:`-ссылки. Хранится нормализованный JSON + текст.
- Prisma (параметризованные запросы) → SQL-инъекции невозможны; сырой SQL только в поиске, и там — параметры.

**Файлы**
- Лимиты: 25 МБ на файл, 10 файлов за раз, квота на задачу и доску.
- Тип определяется **по сигнатуре файла**, а не по расширению/`Content-Type`.
- Белый список: изображения, pdf, архивы, офисные документы, текст/код. Исполняемые — запрет.
- Картинки **перекодируются через sharp** → это убивает полиглот-файлы и вырезает EXIF (гео-метки).
- Хранятся вне webroot под сгенерированными именами; отдаются **только через авторизованный роут** с проверкой доступа к задаче, `Content-Disposition: attachment` для не-картинок, `Content-Security-Policy: sandbox`.
- SHA-256 чексумма → дедупликация и защита от повторной заливки одного и того же.

**Rate limiting** (Redis)
- Глобально по IP, отдельно и жёстче — на `/auth/*` (10 попыток / 10 мин), на загрузку файлов, на создание сущностей, на поиск.
- Bruteforce-защита кодов входа: код одноразовый + окно 2 минуты + лимит попыток.

**Прочее**
- Секреты только в `.env` (600, владелец — сервисный пользователь), в репозитории — `.env.example`.
- Webhook бота: секретный путь + сверка `X-Telegram-Bot-Api-Secret-Token`, + опционально allowlist подсетей Telegram.
- Логи без PII и токенов; отдельный поток `SecurityEvent`.
- Ошибки наружу — обезличенные, `requestId` для сопоставления с логом.
- Зависимости: `npm audit` в CI, Dependabot/Renovate.
- Резервные копии БД шифруются.
- Graceful shutdown, healthcheck-ручки, отдельный непривилегированный пользователь в контейнерах.

## 8. Бизнес-правила (то, ради чего всё)

### 8.1 Обязательное объяснение
Сервер **требует** непустую причину (мин. 10 символов) при:
1. Переводе задачи в **ON_HOLD**;
2. Любом **движении назад** по пайплайну (QA → IN_PROGRESS, READY → QA и т. п.) — типичный кейс «тестер вернул»;
3. **Изменении дедлайна** (`dueDate`) у задачи, где он уже был;
4. Снятии/смене исполнителя у задачи в работе (добавил от себя — на практике это главный источник «а кто это тут всё переиграл»).

Реализация: поле `reason` в теле запроса; в **одной транзакции** — обновление задачи + создание системного комментария с причиной + запись в `Activity` + постановка уведомлений в очередь. Без причины — `422` и подсветка поля на фронте. Причину нельзя обойти через «сначала подвинул, потом написал».

### 8.2 Дедлайны и подсветка
Состояния карточки, считаются в таймзоне пользователя:
| Состояние | Условие | Вид |
|---|---|---|
| `overdue` | `dueDate < now`, задача не в DONE | красная рамка + пульсация бейджа |
| `today` | дедлайн сегодня | оранжевый бейдж «Сегодня» |
| `soon` | < 24 ч | янтарный |
| `upcoming` | < 3 дней | жёлтая точка |
| `normal` | дальше | серый |
| `done` | задача завершена | приглушённый |

Плюс: напоминания в Telegram за 24 ч и за 2 ч до дедлайна (шедулер BullMQ), ежедневный утренний дайджест «что горит».

### 8.3 Прочие правила
- WIP-лимиты по колонкам: мягкое предупреждение (или жёсткий запрет — настройка доски).
- Перевод в QA — можно требовать назначенного тестировщика (настройка).
- Перевод в DONE проставляет `completedAt` и считает cycle time.
- Блокирующие связи: нельзя перевести в DONE задачу, у которой есть незакрытые `BLOCKED_BY` (предупреждение).
- Архив вместо удаления; жёсткое удаление — только OWNER, с подтверждением ввода ключа задачи.

## 9. Уведомления

### 9.1 Матрица событий
| Событие | Кого уведомляем |
|---|---|
| Назначили исполнителем | нового исполнителя (+ старого, что снят) |
| Назначили тестировщиком | тестировщика |
| Смена статуса | автора, исполнителя, тестировщика, наблюдателей, контрибьюторов |
| **Возврат назад / ON_HOLD (с причиной)** | всех участников, **высокий приоритет**, причина в тексте |
| Изменён дедлайн | всех участников |
| Новый комментарий | всех участников, кроме автора комментария |
| Упоминание `@user` | упомянутого — **всегда**, даже если он выключил остальное |
| Приложен файл | участников |
| Задача создана на тебя | исполнителя |
| Скоро дедлайн (24ч/2ч) | исполнителя |
| Просрочено | исполнителя + автора |
| Добавили на доску | приглашённого |
| Утренний дайджест 09:00 | всех, у кого есть активные задачи |

### 9.2 Как доставляем
1. Транзакция в API завершилась → в BullMQ летит событие.
2. Воркер разворачивает событие в список получателей, **исключая инициатора**, применяет настройки пользователя (типы, тихие часы, «только упоминания»), схлопывает дубли.
3. Пишет `Notification` в БД (для колокольчика в UI) → пушит в Socket.IO → отправляет в Telegram через бота.
4. Батчинг: если по одной задаче за 60 секунд накопилось несколько событий — они склеиваются в одно сообщение (иначе бот превращается в спам).
5. Ретраи с экспоненциальным backoff; `403 Forbidden: bot was blocked` → ставим `botBlocked = true` и больше не долбим.
6. Соблюдение лимитов Telegram (≈30 сообщений/сек) — rate-limiter в воркере.

### 9.3 Сообщение в Telegram
```
🔴 OPS-128 · Поправить экспорт в CSV
Тестировщик вернул задачу: QA → В работе
Причина: «Не экспортируются строки с кириллицей»
— Ирина Смирнова · доска «Операции»
[ Открыть ]  [ Взять в работу ]  [ Ответить ]
```
Кнопки — inline-клавиатура: открыть в вебе, быстро сменить статус (с проверкой прав!), ответить комментарием прямо из Telegram (`force_reply`).

## 10. Telegram-бот

**Команды:** `/start` (вход/привязка), `/me` (профиль и связка), `/tasks` (мои активные, с фильтрами), `/today` (что горит сегодня), `/boards`, `/mute` и `/unmute`, `/settings` (тонкая настройка уведомлений inline-кнопками), `/help`, `/logout` (отозвать сессии).

**Сценарии:**

- Ответ на уведомление обычным сообщением (reply) → создаёт комментарий в задаче. Автор автоматически становится контрибьютором.
- Инлайн-режим: `@bot OPS-1` → быстрый поиск задачи и отправка карточки в чат (этап 2).
- Бот сам обновляет `displayName`/`avatar`, если человек сменил их в Telegram (и если аватар не загружен вручную).
- Обработка блокировки бота, миграции чата, ошибок API.

## 11. Интерфейс (UI/UX)

### 11.1 Дизайн-система
Своя, на Radix + Tailwind. Токены в CSS-переменных → тёмная/светлая тема без дублирования классов.
Компоненты: Button, IconButton, Input, Textarea, Select, Combobox, Checkbox, Switch, Radio, Dialog, Sheet (bottom-sheet на мобиле), DropdownMenu, ContextMenu, Tooltip, Popover, Tabs, Avatar/AvatarGroup, Badge, Chip, Progress, Skeleton, EmptyState, Toast, CommandPalette, DatePicker, RichTextEditor, FileDropzone.

Внимание к деталям: скелетоны вместо спиннеров, оптимистичные апдейты, `prefers-reduced-motion`, фокус-кольца, ARIA, контраст ≥ 4.5:1.

### 11.2 Экраны
1. **Вход** — большая кнопка «Войти через Telegram», QR-код для входа с десктопа через телефон, статус ожидания.
2. **Онбординг** — имя + аватар (кроп, drag-n-drop), выбор таймзоны/языка.
3. **Список досок** — карточки с прогрессом, количеством просроченных, аватарами команды, «избранные» доски.
4. **Доска (Kanban)** — 6 колонок, счётчики и WIP-лимиты, drag-n-drop, свернуть колонку, свимлейны (по исполнителю / приоритету / эпику), фильтры (люди, лейблы, приоритет, срок, поиск), сохранённые фильтры, полоса аватаров команды сверху.
5. **Карточка задачи** — модалка на десктопе / полноэкранная страница на мобиле; левая колонка: описание, чек-листы, вложения, комментарии; правая: статус, исполнитель, тестировщик, приоритет, лейблы, сроки, оценки, связи; вкладки «Комментарии / История / Всё».
6. **Бэклог (банк задач)** — таблица + групповые операции (массово назначить, проставить приоритет, отправить на доску), drag из бэклога прямо в колонку.
7. **Люди** — сетка участников: аватар, роль, загрузка (сколько в работе, сколько просрочено), клик → панель с его задачами и **кнопкой «Создать задачу на него»** (как просил заказчик).
8. **Мои задачи** — сквозной кросс-бордовый список: сегодня / неделя / просрочено.
9. **Дашборд** — throughput, среднее время цикла, распределение по людям и приоритетам, «бутылочные горлышки» (где задачи стоят дольше всего).
10. **Админка (SUPERADMIN)** — все доски, все задачи, пользователи и роли, глобальный банк бэклога, лента аудита, статус очереди уведомлений.
11. **Настройки** — профиль, уведомления (по типам и каналам), тихие часы, тема, язык, активные сессии.

### 11.3 Мобильный опыт (отдельный приоритет)
- Колонки — горизонтальный **snap-scroll**, свайп между колонками, вкладки-переключатели сверху с счётчиками.
- Перетаскивание: long-press (250 мс) → карточка «поднимается», автоскролл к краям экрана, **haptic feedback**; альтернатива для тех, кому неудобно таскать — кнопка «Переместить» с выбором колонки в bottom-sheet (это важно: DnD на телефоне никогда не должен быть единственным способом).
- Все модалки → bottom-sheet со свайпом вниз.
- Крупные тач-цели (≥44px), нижняя навигация, кнопка «+» большим пальцем.
- PWA: установка на домашний экран, офлайн-кеш прочитанного, push-уведомления (в дополнение к Telegram).
- Safe-area (чёлка/жесты iOS), без залипаний зума на инпутах (font-size ≥ 16px).

### 11.4 Интерактивность
- **Реалтайм**: карточки двигаются у всех сразу; «Ирина печатает комментарий…»; аватарки тех, кто сейчас смотрит задачу.
- **Командная палитра** `Cmd/Ctrl+K`: перейти к задаче по ключу, создать задачу, сменить доску, назначить, поменять статус.
- **Горячие клавиши** (как в Linear): `C` — создать, `A` — назначить, `L` — лейбл, `P` — приоритет, `D` — дедлайн, `E` — редактировать, `/` — поиск, `?` — подсказка.
- Быстрое создание задачи прямо в колонке (одна строка + Enter).
- Inline-редактирование заголовка, drag аватара на карточку = назначить.
- Undo для деструктивных действий (тост «Отменить» 8 секунд).
- Вставка скриншота из буфера прямо в комментарий (Ctrl+V).

## 15. Деплой на VPS

**Состав:** Caddy (TLS+статика+reverse-proxy) → api (Fastify) + bot (grammY) + worker (BullMQ) + PostgreSQL + Redis. Всё в `docker-compose.prod.yml`, тома для БД, Redis и загруженных файлов.

**Шаги:**
1. `git clone`, `cp .env.example .env`, заполнить (BOT_TOKEN, JWT-секреты, домен, пароль БД).
2. `docker compose -f docker-compose.prod.yml up -d --build`.
3. Миграции применяются автоматически при старте api (`prisma migrate deploy`).
4. Caddy сам выпускает сертификат Let's Encrypt.
5. Установка вебхука бота одной командой.

**Эксплуатация:** ежедневный `pg_dump` по cron с ротацией 14 дней и шифрованием, логи в journald с ротацией, `docker compose logs`, healthcheck-мониторинг, uptime-бот. Обновление: `git pull && docker compose up -d --build` (с zero-downtime для api через два инстанса — опционально).

**Минимальные требования VPS:** 2 vCPU / 4 ГБ RAM / 40 ГБ SSD. Отдельный non-root пользователь, ufw (только 22/80/443), fail2ban, SSH по ключу.

### Что сознательно НЕ сделано

Это не забытые пункты, а отложенные решения — каждое с причиной.

| Что | Почему отложено |
|---|---|
| **E2E-тесты (Playwright)** | Есть 128 unit- и интеграционных тестов, включая проверку авторизации и прав на уровне HTTP. E2E требуют поднятой инфраструктуры в CI; добавляются отдельным этапом. |
| **Интеграционные тесты с реальной БД** | Тесты специально не требуют Postgres и Redis, чтобы гоняться на каждом коммите за секунду. Тесты с БД — следующий шаг (testcontainers). |
| **Английская локализация** | Интерфейс на русском. Поле `locale` в модели и разделение текстов подготовлены, но словарей пока нет. |
| **Спринты и story-poker** | В ТЗ не заявлено; поле `storyPoints` есть, модель спринта — нет. Добавляется без ломающей миграции. |
| **Push-уведомления в браузере** | Есть манифест, иконки и сервис-воркер (установка на телефон и офлайн-оболочка работают). Web Push требует VAPID-ключей и отдельного согласия — а уведомления и так приходят в Telegram. |
| **Хранение файлов в S3** | Для одного VPS диск проще и дешевле. Замена — только `lib/files.ts`, остальной код не меняется. |
| **Полнотекстовый поиск `tsvector`** | Сейчас поиск по подстроке с GIN-индексом на триграммах. До сотен тысяч задач этого достаточно. |
| **Экспорт CSV/JSON** | Данные доступны через API; выгрузка в интерфейсе — следующий этап. |

### Найденное и исправленное при проверке

- **Зависание при недоступном Redis.** Основной клиент копил команды в офлайн-очереди
  без ограничения — каждый HTTP-запрос повисал навсегда на лимитере частоты.
  Теперь команды падают быстро, лимитер пропускает запрос, сервис деградирует, а не умирает.
- **500 вместо 403 на чужом Origin.** Плагин CORS бросал исключение; теперь просто
  не выдаёт заголовки, а мутирующие запросы отсекает явная проверка Origin.
- **`prisma` был в devDependencies**, хотя контейнер запускает `prisma migrate deploy`
  после `npm prune --omit=dev`. Миграции в проде не применились бы.
- **Сборка фронтенда из корня** не находила конфигурацию Tailwind (в Docker сборка
  идёт именно из корня). Пути в `vite.config.ts`, `postcss.config.js` и
  `tailwind.config.ts` сделаны абсолютными.
- **Иконки PWA** были заявлены в манифесте, но файлов не существовало — сгенерированы.
- **`formatRelative`** округлял вверх: «30 секунд назад» показывалось как «1 мин назад».

## 19. Второй проход: что добавлено по итогам ревизии

После сборки проекта прошёл по функционалу ещё раз — глазами человека,
который будет пользоваться этим каждый день. Ниже то, что добавлено,
и почему это не мелочи.

### Подключено то, что было заведено, но не использовалось

Три вещи существовали в коде «на будущее» и работали бы против нас:
модель без интерфейса выглядит как забытая функция.

| Что | Стало |
|---|---|
| Модель `SavedView` | Сохранённые фильтры: личные и общие для доски, переключение одним кликом |
| Состояние `swimlane` | Дорожки по исполнителю, приоритету или типу |
| Хелпер `toast.undo` | Архивация задачи с возможностью отменить прямо из тоста |

### Новое

- **Меню быстрых действий на карточке** (кнопка «…» и правая кнопка мыши):
  взять в работу, сменить исполнителя, переложить в колонку, выставить срок
  «сегодня / завтра / через неделю», приоритет, копировать ссылку или ключ,
  дублировать, в архив. Большинство ежедневных действий больше не требует
  открывать задачу.
- **Дублирование задач** (`POST /api/tasks/:id/duplicate`), в том числе сразу
  несколько копий. Копируются содержание и чек-листы, но не чужое обсуждение.
- **Реакции на комментарии.** Короткое «понял» перестаёт быть отдельным
  сообщением — обсуждение снова можно читать целиком.
- **Быстрые фильтры-чипами**: «На мне», «Просрочено», «Сегодня», «Свободные».
  Раньше это было спрятано за два клика в поповере, то есть практически не существовало.
- **Выгрузка CSV** с учётом фильтров — с BOM для Excel и защитой от подстановки формул.
- **Просмотр архивных задач** — отдельный переключатель в фильтрах.
- **Лайтбокс для вложений**: скриншоты открываются на месте, со стрелками и Esc.
- **Черновики комментариев** сохраняются локально и переживают перезагрузку.
- **Автоссылки на задачи**: `OPS-12` в тексте становится ссылкой.
- **Роли участников** в карточке задачи показываются явно, а не только аватарами.
- **Справка по горячим клавишам** по `?`.

### Исправлено во втором проходе

- **Горячие клавиши не работали на русской раскладке.** `event.key` для клавиши C
  на ЙЦУКЕН — это «с», поэтому биндинг `c` не срабатывал бы у большей части
  команды. Теперь сочетания сверяются и по символу, и по физической клавише.
- **Кнопка меню на карточке начинала перетаскивание** — нажатие гасится до dnd-kit.
- **На телефоне кнопка «Создать» на доске создавала доску, а не задачу.**
- **В карточке задачи на узком экране** свойства (статус, исполнитель, срок)
  теперь показываются выше описания — при беглом просмотре важнее именно они.
- Убран мёртвый код: `bigIntToString`, `recordActivityStandalone`,
  `publishActivity`, дублирующая регулярка для ключей задач.
- Убраны приведения `as never` в клиентском коде: добавлены «входные» типы
  zod-схем (`CreateTaskPayload` и другие), где даты — строки, а поля со
  значениями по умолчанию необязательны.

## 20. Реалтайм: доведено до конца

Проверил сквозное покрытие событий и нашёл разрыв: клиент подписывался
на комнату задачи, но обработчиков не было — то есть открытая карточка
и лента комментариев жили без обновлений.

### Что исправлено

| Было | Стало |
|---|---|
| Комментарии появлялись только после перезагрузки | Приходят живьём, вставляются в кеш из самого события |
| Реакции и вложения в открытой задаче не обновлялись | Обновляются сразу |
| Удалённая задача оставалась открытой | Карточка закрывается с понятным сообщением |
| Архивация не доходила до открытой карточки | Доходит |
| `session:revoked` объявлен, но не отправлялся | «Выйти на всех устройствах» разлогинивает вкладки мгновенно |
| Обрыв сокета выглядел как обычная работа | Отметка «обновления приостановлены» на доске |
| Событие `activity:created` не использовалось | Убрано из контракта: лента обновляется вместе с доской |

### Что появилось попутно

- **«Сейчас смотрят»** — аватары коллег, открывших ту же задачу.
  Дешёвая защита от параллельной работы над одним и тем же.
- **«Мои задачи» обновляются** при получении уведомления.
- Свои же события не вызывают лишних перезапросов: они уже применены
  ответом на мутацию, повторный запрос давал бы только мигание.

### Проверка

Сквозная сверка «сервер отправляет → клиент слушает» по всем шестнадцати
событиям контракта: неслушаемых не осталось.
