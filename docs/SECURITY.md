# Безопасность

Документ описывает, от чего защищаемся и как именно. Здесь же — то,
что нужно сделать руками при установке.

---

## 1. Авторизация через Telegram

Поддерживаются три способа входа, все проверяются криптографически.

### 1.1 Одноразовый код через бота (основной)

1. Браузер запрашивает код: сервер генерирует 24 случайных байта, сохраняет
   в базе **только SHA-256 хеш** и отдаёт клиенту сам код вместе с коротким
   **кодом подтверждения** (4 символа), который показывается на экране.
2. Пользователь открывает `t.me/<bot>?start=<код>`.
3. Бот получает сообщение **от серверов Telegram** — значит, `telegram_id`
   отправителя достоверен. Но вход **не подтверждается автоматически**:
   бот показывает, какое устройство просится внутрь, его адрес и тот же
   код подтверждения, и ждёт нажатия «Это я, войти».
4. Только после подтверждения браузер может обменять код на пару токенов.

**Почему подтверждение обязательно.** Код знает тот, кто его запросил,
а подтверждает тот, кто нажал кнопку в Telegram. Без явного шага достаточно
прислать человеку ссылку на *свой* код — он нажмёт `/start`, и посторонний
получит сессию под его именем. Сверка кода на двух экранах закрывает это:
человек видит, что на его компьютере показан другой код, и жмёт «Это не я».

Защита:
- срок жизни 2 минуты;
- одноразовость обеспечена атомарным `UPDATE ... WHERE status = 'APPROVED'`
  — параллельный запрос получит ноль строк;
- в базе нет самого кода, только хеш;
- отклонение гасит код и пишет событие в журнал безопасности;
- в коде подтверждения нет символов, которые легко перепутать (0/O, 1/I/L);
- на ручку выдачи и обмена кодов наложен жёсткий лимит частоты.

### 1.2 Telegram Login Widget

`data_check_string` собирается из отсортированных полей, ключ — `SHA256(bot_token)`,
подпись сверяется **за постоянное время** (`crypto.timingSafeEqual`).
Дополнительно:
- `auth_date` не старше 5 минут;
- отклоняем данные «из будущего» (сдвиг часов — признак подделки);
- значение `hash` кладётся в Redis на 10 минут → повторное использование
  той же подписи невозможно;
- `photo_url` принимается только по HTTPS.

### 1.3 Telegram Mini App

Отличается схемой ключа: `secret = HMAC-SHA256("WebAppData", bot_token)`.
Проверки свежести и защиты от повтора — те же.

## 2. Токены и сессии

| Что | Где живёт | Срок |
|---|---|---|
| Access-токен (JWT HS256) | **в памяти вкладки**, не в localStorage | 15 минут |
| Refresh-токен | cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/auth` | 30 дней |

Почему access-токен не в `localStorage`: при XSS его нельзя «унести» —
после закрытия вкладки он исчезает. Восстановление сессии идёт через
refresh-cookie, которую JavaScript прочитать не может.

**Ротация с обнаружением повторного использования.** Каждый refresh выдаёт новую
пару и помечает старый токен использованным. Если пришёл уже использованный
токен — значит, его кто-то украл: отзывается вся «семья» сессий, а пользователю
приходит уведомление в Telegram.

**Мгновенный отзыв.** У пользователя есть счётчик `tokenVersion`; его инкремент
делает недействительными все выданные JWT. Отдельные сессии отзываются через
Redis-денилист, который проверяется на каждом запросе.

На каждом запросе также сверяются: активность учётной записи, актуальная роль
и состояние сессии. Блокировка сотрудника срабатывает мгновенно, а не через 15 минут.

## 3. Права доступа

Матрица прав живёт в `packages/shared/src/permissions.ts` и покрыта тестами.
Проверка выполняется **на сервере** в каждом обработчике; клиент лишь прячет
кнопки, чтобы не показывать заведомо недоступное.

Правила, о которых легко забыть:
- чужой комментарий не может редактировать никто, включая владельца доски
  (удалить — может администратор);
- владельца доски нельзя понизить или исключить, только передать владение;
- администратор не может выдать роль, равную своей или выше;
- архивная доска доступна только на чтение;
- отсутствие доступа к доске отдаётся как **404**, а не 403 — чтобы нельзя было
  перебором узнать, какие доски существуют.

## 4. Ввод и вывод

**Валидация.** Каждый запрос разбирается zod-схемой: типы, длины, форматы,
белый список полей. Неизвестные поля отбрасываются.

**Форматированный текст.** Документ TipTap приходит как JSON и проходит через
собственный санитайзер (`lib/sanitize.ts`):
- белый список узлов и марок;
- `javascript:`, `data:` и прочие протоколы в ссылках вырезаются;
- у ссылок принудительно проставляется `rel="noopener noreferrer nofollow"`;
- цвета текста — только из фиксированной палитры;
- ограничены глубина вложенности (12), число узлов (4000) и длина текста;
- управляющие символы удаляются.

**SQL.** Всё через Prisma — параметризованные запросы. Сырого SQL в бизнес-логике нет.

## 5. Файлы

- Тип определяется **по сигнатуре файла**, а не по `Content-Type` от клиента.
- Изображения **перекодируются** через sharp. Побочный, но главный эффект:
  файл на диске гарантированно является картинкой (полиглот-файлы не выживают),
  а EXIF с геометками вырезается.
- SVG **запрещён** — он умеет исполнять скрипты.
- Имя файла на диске генерирует сервер (16 случайных байт); исходное имя
  хранится отдельно и очищается от путей и управляющих символов.
- Файлы лежат вне webroot и отдаются только через авторизованный роут.
- Не-картинки отдаются с `Content-Disposition: attachment`,
  `X-Content-Type-Options: nosniff` и `Content-Security-Policy: sandbox`.
- Загрузки, не привязанные к задаче, удаляются через сутки фоновой джобой.
- Считается SHA-256 — для дедупликации и контроля целостности.

**Подписанные ссылки.** Тег `<img>` не умеет отправлять заголовок `Authorization`,
поэтому картинки отдаются по ссылке с подписью `?t=<exp>.<hmac>`. Подпись
привязана к конкретному файлу, живёт 7 дней и округлена до суток —
так URL стабилен и кешируется браузером. В базе картинки хранятся каноническим
путём без подписи; свежая подпись подставляется при отдаче.

> Учтите: такая ссылка — это «капабилити». Кто получил ссылку, тот получил файл
> (до истечения срока). Для внутреннего инструмента это осознанный компромисс:
> ровно так ссылки и пересылают коллегам.

## 6. Сеть и заголовки

- **HTTPS обязателен**, HSTS с `preload`.
- **CSP** для API: `default-src 'none'` — исполняемому контенту там взяться неоткуда.
- **CORS**: белый список ровно из разрешённых Origin, `credentials: true`.
- **CSRF**: `SameSite=Strict` на refresh-cookie **плюс** серверная проверка
  заголовка `Origin` на всех мутирующих запросах. Одного механизма мало.
- `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `X-Frame-Options`.

**Ограничение частоты** (Redis):

| Область | Лимит по умолчанию |
|---|---|
| Общий | 300 запросов / минуту на пользователя или IP |
| `/api/auth/*` | 12 попыток / 10 минут |
| Загрузка файлов, поиск | 60 / минуту |
| Статус кода входа | 120 / минуту (это поллинг) |

## 7. Вебхук Telegram

- Путь содержит секрет: `/telegram/<TELEGRAM_WEBHOOK_SECRET>`.
- Дополнительно сверяется заголовок `X-Telegram-Bot-Api-Secret-Token`.
- Служебный API `/api/internal/*` закрыт общим секретом,
  который сверяется за постоянное время.

## 8. Аудит

Пишутся два потока:
- `Activity` — что происходило с задачами и досками (видно пользователям);
- `SecurityEvent` — входы, отзывы сессий, смены ролей, отказы в доступе,
  обнаружение повторного использования токена (видно суперадмину).

В логах нет токенов, cookie, `initData` и заголовков авторизации — они
вырезаются на уровне логгера.

## 9. Что сделать руками при установке

1. Сгенерировать секреты: `openssl rand -base64 48` для `JWT_SECRET`,
   `openssl rand -base64 32` для `INTERNAL_API_SECRET`,
   `openssl rand -hex 16` для `TELEGRAM_WEBHOOK_SECRET`.
   **Не переиспользовать один секрет в разных полях.**
2. `chmod 600 .env`, владелец — сервисный пользователь.
3. Заполнить `SUPERADMIN_TELEGRAM_IDS` — иначе некому будет администрировать.
4. Не публиковать порты Postgres и Redis наружу (в `docker-compose.prod.yml`
   они намеренно только `expose`).
5. Включить `ufw` (скрипт `deploy/setup-server.sh` это делает), запретить
   вход по паролю в SSH.
6. Настроить бэкапы (`deploy/backup.sh`) и задать `BACKUP_PASSPHRASE` —
   незашифрованные дампы на арендованном сервере лежать не должны.
7. Держать отдельного бота для разработки: у тестового и боевого бота
   не должно быть общего токена.
8. Регулярно: `npm audit`, обновление образов, `docker compose pull`.

## 10. Известные компромиссы

- **Подписанные ссылки на файлы** — капабилити-URL (см. §5).
- **Аватары** отдаются без авторизации по неугадываемому имени: иначе они
  не отображались бы в письмах, превью и офлайн-кеше.
- **Суперадмин видит всё**, включая чужие доски. Это требование продукта;
  каждое такое действие остаётся в аудите.
- **Поиск** работает через `ILIKE` с GIN-индексом на триграммах. Для сотен
  тысяч задач стоит перейти на полнотекстовый индекс `tsvector`.
